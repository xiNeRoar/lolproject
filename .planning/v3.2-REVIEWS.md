# Cross-AI Plan Review — Milestone v3.2 Frontend Readiness

## Codex Review (OpenAI)

**Summary**

The milestone was well-scoped at the contract level and mostly executed in the right dependency order: backend route changes landed, the OpenAPI spec was updated, and Orval-generated clients reflect the new contract. The main weakness is closure discipline. Several plans were marked complete even though the frontend consumption path and one verification-critical TS cleanup were still open, so the milestone improved backend readiness more than true frontend launch readiness.

**Strengths**

- The API contract flow was designed correctly: route change -> OpenAPI update -> generated client/types. That chain is visible in [`auth.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/artifacts/api-server/src/routes/auth.ts#L92), [`openapi.yaml`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/lib/api-spec/openapi.yaml#L2439), and [`api.schemas.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/lib/api-client-react/src/generated/api.schemas.ts#L45).
- Privacy was treated as a first-class concern in the new player team-stats route. It reuses the shared profile visibility gate instead of inventing route-local logic in [`players.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/artifacts/api-server/src/routes/players.ts#L764).
- The team-stats implementation uses a sensible 2-phase query shape instead of N+1 lookups, which is appropriate for a player-profile endpoint in [`players.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/artifacts/api-server/src/routes/players.ts#L790).
- Codegen sync appears complete across both React client and Zod artifacts, reducing contract drift risk for future work.
- Design-system guidance exists and is centralized in [`DESIGN_GUIDE.md`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/docs/DESIGN_GUIDE.md), which is better than leaving frontend conventions implicit.

**Concerns**

- `HIGH` The milestone did not actually close the auth frontend path. The backend returns `hasPuuid` and `rsoOptIn`, but `useAuth()` still does not expose them to components in [`use-auth.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/artifacts/vclol/src/hooks/use-auth.ts#L16). For a milestone explicitly framed as frontend readiness, that is an end-to-end miss, not a minor follow-up.
- `HIGH` Verification quality was inconsistent. The repo’s own audit trail shows `vods.ts` was declared fixed while 21 `TS7006` errors remained, documented in [`04.1-01-VERIFICATION.md`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/.planning/phases/04.1-v3.1-bug-fixes/04.1-01-VERIFICATION.md#L8). That undermines confidence in phase completion claims.
- `MEDIUM` The new `GET /players/:id/team-stats` route can duplicate or misrepresent history because stats are aggregated by `teamId`, then merged onto every membership row for that team in [`players.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/artifacts/api-server/src/routes/players.ts#L813). Since [`teamMembers.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/lib/db/src/schema/teamMembers.ts#L7) has no uniqueness constraint on `(playerId, teamId)`, rejoin/pending/inactive rows can produce repeated team entries with the same aggregate stats.
- `MEDIUM` The team-stats API is generated but not integrated into any frontend caller. That means the milestone delivered a contract, not a proven UI path. This is acceptable for backend completion, but not for “frontend readiness.”
- `MEDIUM` The team-stats endpoint applies profile visibility only; it does not account for match-level privacy when aggregating stats. If the product intent is that private scrims should not contribute to public-facing aggregates, this route extends an existing privacy-model ambiguity rather than resolving it.
- `LOW` The docs/ownership phase shows weak artifact validation. [`CLAUDE.md`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/CLAUDE.md#L277) embeds a generated section sourced from `PROJECT.md`, but `PROJECT.md` is not present in the repo. That suggests plan acceptance checked narrative completion more than repository state.
- `LOW` `useAuth()` still mixes session auth with `localStorage` fallback in [`use-auth.ts`](C:/Users/User/Desktop/VS%20Code%20Project/lolproject/artifacts/vclol/src/hooks/use-auth.ts#L40). That split source of truth is technical debt and makes future auth-state bugs more likely.

**Suggestions**

- Define milestone completion in end-to-end terms, not artifact terms. “Backend field exists” should not pass if the shared frontend wrapper still drops it.
- Add a required “consumer wired” check for any new generated hook: at least one real caller, or an explicitly accepted deferral.
- Tighten verification gates. If a plan claims “zero TS errors,” require the exact command output to be attached and reviewed before marking complete.
- For team-history endpoints, decide the data model first: one row per membership stint, or one row per team. The current route mixes those concepts.
- Add contract-to-wrapper tests for shared hooks like `useAuth()` so generated schema changes cannot silently stop at the API layer.
- Keep issue hygiene and ownership-doc work out of the critical path for launch-readiness milestones unless they directly unblock execution.

**Risk Assessment**

Overall risk: `MEDIUM`.

The backend contract work is mostly in place, and the privacy gate reuse is a good sign. But the milestone did not fully achieve its stated frontend-readiness goal because shared frontend consumption is incomplete, verification missed a claimed TS fix, and the new team-stats route has unresolved semantics around duplicate memberships and privacy scope. This is recoverable without rework of the whole milestone, but it is not clean launch-ready as executed.
